# Arcflight Event Runner — Canonical Gameplay Rules

**Status:** Canonical design contract, Version 1
**Scope:** Arcflight Core event runner
**Purpose:** Authoritative gameplay reference for implementation, testing, event authoring, UI, and future milestones.
**Implementation authority:** [`ARCFLIGHT_GAMEPLAY_V3_CANONICAL_AUDIT_AND_MILESTONE_MAP.md`](ARCFLIGHT_GAMEPLAY_V3_CANONICAL_AUDIT_AND_MILESTONE_MAP.md)

This document supersedes earlier Arcflight gameplay notes wherever they conflict with the rules below. It records the rules locked during design review. Implementation details may evolve, but code must not silently change these gameplay rules.

---

## 1. Product Definition

Arcflight Core is a GM-authoritative cinematic ship-event runner for Foundry VTT. It runs handcrafted multiplayer ship events using persistent ships, fixed station operators, round-specific actions, PF2e checks, Risk Bids, Focus, reactions, Momentum, Pressure, Hazards, Void Scars, upgrades, rewards, Misfortunes, closeout review, recovery, and persistent ship consequences.

Arcflight Core does **not** require an active voyage, route, destination, port, hex map, travel clock, supply calculation, or travel-event sequence.

An event may be launched from:

- the Arcflight GM panel;
- a macro;
- the Arcflight API;
- a Foundry scene or region;
- an optional MATT trigger;
- a future companion travel or voyage module.

### 1.1 Core start requirements

Starting an event requires only:

1. a valid authored Event Definition;
2. a selected Arcflight ship;
3. station operators;
4. GM authorization.

Optional external context may be attached, but the event runner must not depend on it.

### 1.2 Out of scope for Arcflight Core

The following belong to a possible future companion module:

- origins and destinations;
- route maps and hex progress;
- estimated travel days;
- daily supplies and Arkengine fuel;
- ports, trade, and route services;
- point-to-point voyage planning;
- predetermined travel-event sequencing;
- automatic event triggering from travel progress.

Void Scar rules and repair data remain in Arcflight Core because events create Void Scars. A companion module may later provide port and dockyard workflows that call Core repair functions.

## 2. Canonical Terms

### Event Definition

Immutable handcrafted content describing an event, its rounds, station actions, approaches, Risk Bids, Focus abilities, Hazards, rewards, Misfortunes, media, and closeout branches.

### Event Session

The live GM-authoritative state of one running event: assignments, choices, order, rolls, reactions, Focus, Momentum, Pressure, Hazards, proposed Void Scars, and closeout results.

### Station Operator

The one character or named NPC assigned to a station for the event.

### Action Segment

The resolution window for one occupied station during a round, including pre-roll, roll, result-modification, outcome, and post-resolution reaction windows.

### Risk Bid

An optional authored increase of `+2`, `+5`, or `+8` to the selected action’s DC. The action and Risk Bid resolve from the same PF2e check.

### Focus

A limited resource belonging to an occupied station operator. It activates risky station-specific abilities that use authored triggers, checks, targets, and four-degree outcomes.

### Momentum

The ship-wide positive rhythm bonus generated by successful rounds. Its normal range is `0` to `+3`.

### Pressure

Temporary event strain tracked separately for each station system.

### Hazard

An active tactical problem that affects the current event until removed, expired, replaced, or resolved at closeout.

### Void Scar

A persistent ship impairment occupying one slot of the installed hull’s Void Scar Capacity.

### Catastrophic Breakdown

The crisis triggered when a ship already at maximum Void Scar Capacity would gain another Void Scar.

## 3. Stations, Operators, and Assignment

Arcflight uses five primary stations:

| Station | Pressure System |
|---|---|
| Captain | Crew Morale |
| Engineer | Arkengine |
| Navigator | Levstone Array |
| Watchmaster | Solar Sail Rig |
| Veilwarden | Lifeveil |

### 3.1 One operator per station

- One station may have exactly one operator.
- An operator may be a player character or a named NPC built and run like a normal character.
- Two characters may never jointly operate one station.
- There is no assistant, copilot, or second operator slot.
- A player may control multiple characters or named NPCs, provided each operator occupies a different station.

### 3.2 Fixed assignments

- Station assignments are chosen before Round 1.
- Station assignments remain fixed for the entire event.
- Operators do not change stations between rounds.
- Runtime recovery may transfer control of the same operator to the GM or another user, but it does not reassign that operator to another station.

### 3.3 Unoccupied stations

An unoccupied station:

- takes no action;
- makes no check;
- contributes no success units;
- contributes no failure units;
- receives no Focus;
- does not automatically gain Pressure.

An event may author a specific consequence for leaving a station unoccupied, but there is no universal generic penalty.

## 4. Event Length and Structure

Events use an odd number of authored rounds:

```text
3, 5, 7, 9, or 11
```

- Three- and five-round events should be the normal formats.
- Seven-round events are major set pieces.
- Nine- and eleven-round events are rare chapter-scale or climax events.
- All authored rounds normally play.
- A Catastrophic Breakdown or explicit authored termination rule may end an event early.

Each round is a newly authored chapter of the event. Station actions change from round to round to match the immediate situation and advance the overarching event.

Phases may group rounds for narration, artwork, music, objectives, and stakes, but phases do not own reusable station-action lists. The round owns the exact actions currently available.

---

## 5. Round Lifecycle

Each round follows this sequence:

1. Show the round title, vignette, immediate situation, objective, known stakes, current Momentum, Pressure, and active Hazards.
2. Present exactly three round-specific actions to every occupied station.
3. Each operator chooses one action.
4. Each operator chooses one eligible skill, Lore, save, attack, special ability, or other authored check approach offered by that action.
5. Each operator chooses the action at its base DC or selects one offered `+2`, `+5`, or `+8` Risk Bid.
6. Choose a target only when the selected action or bid affects a selectable station, system, Hazard, consequence, or other subject.
7. The crew chooses the station resolution order for the round.
8. Validate and lock the complete plan.
9. Resolve occupied stations one at a time in the locked order.
10. Skip unoccupied stations.
11. Aggregate success and failure units.
12. Determine the round result.
13. Apply round consequences, Momentum, end-of-round Hazard effects, and Pressure Breaches.
14. Record the round and proceed to the next authored round or event closeout.

### 5.1 Flexible order

Station assignments are fixed, but station resolution order is chosen again every round.

The order is strategically important because earlier stations may create benefits, protections, restrictions, or dangers for later stations.

### 5.2 Planning authority

Players collaborate on the order. The Captain may settle the final sequence when the group cannot agree. The GM resolves invalid plans and rules conflicts.

The Captain does not choose other operators’ actions, approaches, Risk Bids, or Focus use.

## 6. Station Actions and Approaches

### 6.1 Three actions per occupied station

Every occupied station receives exactly three meaningful action choices in every round.

The actions should represent different tactical or narrative approaches to that round’s situation. They should not be three differently worded versions of the same choice.

### 6.2 Approach limit

Each action normally offers:

- one required approach; or
- two selectable approaches.

A signature or unusually broad action may offer a third approach only when the third option has a meaningful mechanical or narrative distinction.

A third approach should differ through at least one of the following:

- result narration;
- Critical Success benefit;
- Failure risk;
- upgrade interaction;
- Risk Bid availability;
- target;
- affected system.

### 6.3 Action commitment

Before the plan locks, every occupied station must have committed:

- one of its three actions;
- one valid approach;
- base DC or one offered Risk Bid tier;
- a valid target when required.

After plan lock, these selections cannot normally change. An explicit reaction, upgrade, Focus ability, or GM correction may alter a locked choice when its rule permits it.

## 7. Risk Bids

### 7.1 Risk Bid selection

Risk Bids are authored variants of the chosen station action. They are not separate actions and do not create a fourth action choice.

For the selected action, the operator chooses:

```text
Base DC
or
Base DC +2
or
Base DC +5
or
Base DC +8
```

Only tiers authored for that action are available. An action may offer no bids, one tier, or several tiers.

### 7.2 Limits

- Maximum one selected Risk Bid per station per round.
- Maximum three selected Risk Bids across the entire round.
- A station using the base action without a bid does not count toward the round limit.

### 7.3 Single-roll resolution

```text
Final DC = Base Action DC + selected Risk Bid
```

The station makes one PF2e check. That single degree of success resolves:

1. the station’s round success or failure units;
2. the normal action benefit;
3. the selected Risk Bid branch;
4. standard Pressure gained from Failure or Critical Failure.

There is never a separate Risk Bid roll.

### 7.4 Outcome handling

| Result | Normal Action | Risk Bid | Round Units |
|---|---|---|---|
| Critical Success | Critical Success benefit | Critical Success bid benefit | 2 success |
| Success | Success benefit | Success bid benefit | 1 success |
| Failure | No normal benefit; no extra normal-action punishment | Failure bid consequence | 1 failure |
| Critical Failure | No normal benefit; no extra normal-action punishment | Critical Failure bid consequence | 2 failure |

A failed action already harms the round and normally adds Pressure. Additional authored punishment comes from the voluntarily selected Risk Bid, not from a second generic normal-action failure branch.

### 7.5 Authored bid effects

Risk Bid effects are not universal by tier. They are written for the specific action and story.

Valid examples include:

- reduce a later station’s DC;
- grant a later station a roll bonus;
- improve a later result by one degree;
- allow a reroll;
- roll twice and keep the better die;
- restore Focus;
- reduce Pressure;
- repair temporary damage;
- remove, suppress, delay, or prevent a Hazard;
- protect a system from a consequence;
- unlock a special action or branch;
- create a next-round benefit;
- change station-order restrictions.

Risk Bid rewards are inherent in the bid. They do not automatically add end-of-event treasure.

### 7.6 Example tiers

An authored Engineer action might use:

- `+2`: reduce the Navigator’s later DC by 2;
- `+5`: improve the Navigator’s final degree by one step;
- `+8`: let the Navigator roll twice and keep the better die; on Critical Success, the Engineer also replenishes Focus.

These are examples, not mandatory tier templates.

## 8. Focus

### 8.1 Ownership

- Every occupied station operator begins the event with 1 Focus by default.
- Focus belongs to the assigned operator and is tracked separately for each occupied station.
- A player controlling multiple station operators tracks Focus separately for each operator.
- An unoccupied station receives no Focus.
- Upgrades or abilities may increase Focus capacity or replenish spent Focus when explicitly authored.

### 8.2 Focus abilities

A Focus ability is a station-specific risky PF2e ability. It may be used on the operator’s own turn or as a reaction during another station’s Action Segment.

Every Focus ability defines:

- trigger;
- timing window;
- Focus cost;
- eligible operator;
- target;
- PF2e check or reroll structure;
- DC source;
- Critical Success effect;
- Success effect;
- Failure effect;
- Critical Failure effect;
- visibility and narration.

Focus is spent before the Focus check or Focus-powered resolution. A bad result does not refund the point unless the ability explicitly says so.

### 8.3 Focus is risky

Focus is not a guaranteed bonus or generic Hero Point. Failure may actively worsen the situation.

#### Example: assist another roll

| Focus Result | Effect on Target Roll |
|---|---:|
| Critical Success | +3 |
| Success | +1 |
| Failure | -1 |
| Critical Failure | -3 |

#### Example: dangerous reroll

| Focus Result | Effect |
|---|---|
| Critical Success | Target rerolls, must use the second result, and gains +2 |
| Success | Target rerolls and must use the second result |
| Failure | No reroll; original result receives -1 |
| Critical Failure | No reroll; original result receives -3 |

#### Example: pressure control

| Focus Result | Effect |
|---|---|
| Critical Success | Reduce Pressure by 1 and replenish the spent Focus |
| Success | Reduce Pressure by 1 |
| Failure | Increase Pressure by 1 |
| Critical Failure | Immediately create the authored Hazard or stronger backlash |

These are templates, not universal Focus abilities.

### 8.4 Focus closeout

Unused Focus disappears at event closeout. Each occupied operator begins a future event with the normal starting amount unless a persistent rule changes that capacity.

Focus does not convert into Momentum or rewards.

## 9. Action Segments and Reaction Windows

Every occupied station resolves through an Action Segment:

1. Reveal the acting station.
2. Confirm its locked action, approach, Risk Bid, and target.
3. Open valid pre-roll reaction windows.
4. Make the station check.
5. Open valid result-modification reaction windows.
6. Finalize the PF2e degree of success.
7. Apply the action and Risk Bid outcomes.
8. Apply success/failure units, Pressure, Hazards, benefits, and consequences.
9. Open valid post-resolution or inter-station reaction windows.
10. Continue to the next station.

Possible reaction sources include:

- Focus abilities;
- station reactions;
- named NPC abilities;
- ship upgrades;
- component abilities;
- Hazard reactions;
- Void Scar restrictions or reactions;
- other authored special abilities.

Every reaction states its exact timing. The runtime must offer eligible reactions before their window closes and must not advance while a required decision is unresolved.

Typical timings include:

- before a station rolls;
- after the die is rolled but before finalization;
- after a Failure;
- when Pressure would be gained;
- when a Hazard would activate;
- after an action fully resolves;
- before the next station begins.

## 10. Momentum

Momentum is a ship-wide positive modifier.

### 10.1 Range

```text
Normal Momentum range: 0 to +3
Event starting Momentum: 0
```

Round 1 normally has no Momentum bonus. An explicit Focus ability, upgrade, or event effect may create an exceptional early bonus or temporary penalty.

### 10.2 Round update

At the end of each round:

```text
Round Success or Critical Round Success
→ Momentum +1, maximum +3

Round Failure or Critical Round Failure
→ Momentum -1, minimum 0
```

Critical degrees change rewards and consequences but modify Momentum by only one step.

The new Momentum value applies beginning with the next station check after the completed round.

### 10.3 Scope

Momentum applies to qualifying event checks, including:

- station actions;
- Risk Bid actions;
- Focus checks;
- Hazard responses;
- Support actions;
- stabilization or repair actions within the event.

### 10.4 No normal negative Momentum

Ordinary failed rounds cannot push Momentum below zero. Negative roll modifiers come only from explicit Focus failures, Hazards, Void Scars, upgrades, event effects, or other authored rules.

### 10.5 Closeout

Remaining Momentum disappears at event closeout. It does not carry forward, become a reward, restore Focus, or convert into another resource.

---

## 11. Arcflight Numeric Caps

For any one qualifying check:

```text
Maximum total Arcflight roll bonus:     +5
Maximum total Arcflight roll penalty:   -5
Maximum total Arcflight DC reduction:   -5
```

These caps apply to Arcflight-generated effects from sources such as:

- Momentum;
- Focus;
- Risk Bids;
- station benefits;
- Hazards;
- Void Scars;
- upgrades;
- named operator abilities;
- pending effects.

The character’s normal PF2e statistic remains separate.

Only one roll-twice-and-keep-the-better effect may apply to one check. Degree improvement cannot exceed Critical Success. Pressure cannot be reduced below zero. Focus replenishment cannot exceed current capacity unless the effect explicitly raises capacity.

## 12. Pressure

Pressure is tracked separately for five station systems:

| Station | Pressure System |
|---|---|
| Captain | Crew Morale |
| Engineer | Arkengine |
| Navigator | Levstone Array |
| Watchmaster | Solar Sail Rig |
| Veilwarden | Lifeveil |

### 12.1 Capacity

```text
Default Pressure Capacity: 2
Maximum upgraded Pressure Capacity: 5
```

Pressure values from zero through the system’s current capacity are safe.

Example:

```text
Capacity 2
Safe: 0, 1, 2
Breach: an increase that would reach 3
```

### 12.2 Standard gain

Unless an authored effect replaces it:

```text
Failure          → +1 Pressure to the action’s associated system
Critical Failure → +2 Pressure to the action’s associated system
```

Focus, Risk Bids, Hazards, upgrades, and event rules may add, reduce, redirect, or prevent Pressure when explicitly authored.

### 12.2.1 Domain-authored Pressure effects

Domain systems that need to apply an authored Pressure consequence use a
separate narrow Pressure planner and application boundary. They do not inject
synthetic actions and they do not receive a general-purpose external Pressure
mutation API.

The only authorized domain source in this slice is
`hazard-address-failure`. Its Address Hazard outcome maps deterministically to
`+1` Pressure for `failure` and `+2` Pressure for `critical-failure`. The
caller supplies the encounter, expected revision, canonical Pressure-system
ID, delta, and a live-bound Hazard source containing the exact active Hazard
index and isolated previous snapshot; it does not supply a Pressure-effect ID
or effect plan. The pure planner constructs the canonical Pressure effect,
including its stable identity and the exact `hazardId` and `addressOutcome`
provenance. The public application accepts the same request and regenerates
the plan internally; returned plans are inspectable analysis data, not
authorization tokens.

Domain-authored effects use the same validated Pressure transition and the same
`voyage.pressure-applied` event contract as action-derived effects. A valid
application changes only Pressure, increments revision once, and emits exactly
one event. Pressure Breach remains a later separate transaction. Existing
action-derived Pressure planner and application APIs, effect records, event
shape, and externally visible behavior remain unchanged. The live Hazard must
remain active at the requested index, be a system Hazard whose Pressure system
matches the request, permit Address Hazard, and remain semantically equal to
the supplied previous snapshot; moved or changed Hazards are stale. A valid
domain plan contains exactly one effect, and its identity includes system,
outcome, and expected revision in addition to encounter, stage, round, source,
and Hazard identity.

### 12.3 Pressure Breach

When a system would rise above its current capacity:

1. create one matching active Hazard;
2. create one matching lasting Void Scar proposal;
3. reset that system’s Pressure to 0.

A single pressure-gaining effect normally creates only one breach, even if it adds multiple Pressure. Additional breaches require explicit authored text.

### 12.4 Closeout

After all unresolved Hazard closeout consequences and resulting breaches are processed, all remaining ordinary Pressure resets to zero.

## 13. Hazards

Hazards are urgent tactical problems during the event.

### 13.1 Sources

A Hazard may be created by:

- a Pressure Breach;
- an authored round or event development;
- a Focus Failure or Critical Failure;
- a Risk Bid consequence;
- another Hazard escalating.

A Pressure Breach creates both a Hazard and a Void Scar. Hazards from other sources do not automatically create a Void Scar.

### 13.2 Player-visible information

When revealed, a Hazard must show:

- name;
- affected system or event area;
- current effect;
- activation timing;
- how it may be removed;
- what happens if ignored.

The GM may retain hidden escalation or narrative information, but player decisions must not rely on undisclosed mechanical punishment.

### 13.3 Activation timing

Each Hazard defines one or more timings, such as:

- immediate;
- before the next station acts;
- at the start of the next round;
- at the end of each round;
- when a named station acts;
- when a specified result occurs;
- at event closeout.

Immediate activation should be used only when interruption is part of the authored fiction.

### 13.4 Ongoing effects

Hazards should change decisions rather than only subtract numbers. They may:

- modify DCs;
- restrict station order;
- disable a Risk Bid;
- prevent Focus recovery;
- add Pressure;
- block an upgrade;
- alter available actions;
- create a countdown;
- threaten an authored consequence.

### 13.5 Address Hazard action

Addressing a Hazard normally replaces the eligible station’s regular action for that round.

A Focus ability, Risk Bid, upgrade, or other authored effect may remove or suppress a Hazard without consuming the station action.

### 13.6 Hazard response

| Result | Effect | Round Units |
|---|---|---|
| Critical Success | Remove Hazard and apply additional authored benefit | 2 success |
| Success | Remove Hazard | 1 success |
| Failure | Hazard remains; affected system gains 1 Pressure | 1 failure |
| Critical Failure | Hazard remains; affected system gains 2 Pressure | 2 failure |

An especially dangerous Hazard may define an additional disclosed consequence.

### 13.7 Hazard limits

Each pressure system normally supports one active system Hazard.

When another Hazard would occupy the same system slot, the authored rule must choose one:

- escalate the existing Hazard;
- replace it;
- trigger its consequence;
- extend its duration;
- add Pressure instead.

Event Hazards such as a boarding party, psychic storm, collision course, or enemy lock do not occupy a system slot unless explicitly attached to one.

### 13.8 Escalation and countdowns

Hazards may use authored stages such as Warning, Dangerous, and Critical, or use a countdown. Most Hazards should remain simple and use one state.

### 13.9 Closeout

```text
Resolved Hazard
→ no additional effect

Unresolved Hazard
→ apply its authored closeout consequence
→ remove the Hazard
```

An unresolved Hazard does not automatically create another Void Scar unless its closeout effect explicitly says so.

## 14. Void Scars

A Void Scar is a persistent impairment affecting ship operation until repaired or removed.

### 14.1 Hull capacity ownership

The installed hull defines base Void Scar Capacity:

```js
flags.arcflight.system.voidScarCapacity
```

The ship stores active Void Scars separately. Effective capacity is derived from the installed hull plus valid upgrade modifiers.

### 14.2 Canonical hull capacities

| Hull | Void Scar Capacity |
|---|---:|
| Void Skiff | 2 |
| Sloop | 3 |
| Cutter | 4 |
| Brigantine | 5 |
| Frigate | 6 |
| Galleon | 7 |
| Hammerhead | 7 |
| Arkcruiser | 9 |
| Dread Caravel | 9 |
| Cathedral Ship | 10 |
| Leviathan-Class Platform | 12 |

Capacity is authored directly on each hull. Runtime must not infer it from tier or expansion slots.

### 14.3 Scar record

Each Void Scar defines:

- stable ID and name;
- affected system;
- description;
- operational effects;
- base repair cost;
- base repair time;
- repair DC source;
- eligible repair checks;
- required facilities;
- compatible field-repair tags;
- media and narration.

### 14.4 Normal repair

Without a special repair resource, removing a Void Scar requires:

1. docking at a suitable port or drydock;
2. required facilities;
3. money;
4. repair time;
5. one Very Hard authored Crafting, Engineering Lore, or other eligible repair check.

The repair check modifies final cost and time. It does not make the Scar permanently unrepairable.

| Repair Result | Final Gold Cost | Final Repair Time |
|---|---:|---:|
| Critical Success | 50% of base | 50% of base |
| Success | 75% of base | 75% of base |
| Failure | 125% of base | 125% of base |
| Critical Failure | 150% of base | 150% of base |

Round fractional costs or time upward according to the implementation’s chosen unit.

### 14.5 Field Repair Resources

A successful event may offer a Field Repair Resource as an authored reward item.

A normal Field Repair Resource:

- is consumed when used;
- removes one compatible Void Scar;
- does not require docking;
- does not require gold;
- does not require the normal Very Hard repair check.

Normal versions should usually be system-specific. Rare or enhanced versions may affect broader Scar categories. The item defines its exact timing and any safe-rest requirement.

## 15. Catastrophic Breakdown

### 15.1 Trigger

```text
Current Void Scars = Hull Void Scar Capacity
A new Void Scar would be gained
→ do not add another Scar
→ trigger a Catastrophic Breakdown for the affected system
```

A ship may operate while at maximum capacity. The Breakdown occurs only when another Scar would be added beyond that maximum.

### 15.2 Immediate effects

A Catastrophic Breakdown:

1. disables the affected system;
2. creates a mandatory Catastrophic Hazard;
3. finishes the action that caused it;
4. pauses normal station resolution;
5. begins an Emergency Response;
6. prevents ordinary continued operation until stabilized.

Possible system crises include:

- Crew Morale: Mutiny or Total Panic;
- Arkengine: Arkengine Cascade;
- Levstone Array: Uncontrolled Descent;
- Solar Sail Rig: Complete Rig Collapse;
- Lifeveil: Shipwide Lifeveil Failure.

### 15.3 Emergency Response

The affected station leads a small authored group challenge. Other occupied stations may contribute according to the Breakdown definition.

| Emergency Result | Canonical Effect |
|---|---|
| Critical Success | Stabilize the Breakdown; system returns in severely limited state; event may continue; apply authored emergency benefit |
| Success | Stabilize the Breakdown; system remains disabled for the rest of the event; event may resume; ship requires repair before normal later operation |
| Failure | Breakdown remains unstable; event becomes an Overall Event Failure; ship must retreat, anchor, receive aid, or enter an authored emergency situation |
| Critical Failure | Event becomes a Critical Overall Event Failure; apply authored disaster; ship becomes stranded, disabled, captured, forced down, or otherwise unable to continue |

A Catastrophic Breakdown does not automatically destroy the ship unless the event explicitly permits destruction and the GM confirms it.

### 15.4 Stabilization is not repair

Stabilizing a Breakdown does not:

- remove a Void Scar;
- restore Scar capacity;
- fully restore the system;
- eliminate dock or field-repair requirements.

### 15.5 Multiple Breakdowns

Only one Catastrophic Breakdown should normally exist at a time. If another would occur before the first is resolved, apply the authored disaster consequence rather than stacking ordinary Breakdown records.

## 16. Round Scoring

Individual station results create units:

```text
Critical Success → 2 success units
Success          → 1 success unit
Failure          → 1 failure unit
Critical Failure → 2 failure units
```

### 16.1 Round result ladder

```text
Critical Round Success
→ success units are at least twice failure units

Round Success
→ success units equal or exceed failure units
→ but do not meet the Critical Success threshold

Critical Round Failure
→ failure units are at least twice success units

Round Failure
→ failure units exceed success units
→ but do not meet the Critical Failure threshold
```

A round with zero success units and zero failure units must use an explicit authored fallback. The ratio formulas must not classify `0 / 0` as a critical result.

### 16.2 Round victory weight

For overall event victory:

- Critical Round Success counts as one successful round.
- Round Success counts as one successful round.
- Round Failure counts as one failed round.
- Critical Round Failure counts as one failed round.

Critical degrees change reward or negative points and authored consequences, not the number of rounds won or lost.

---

## 17. Overall Event Result

The event winning threshold is:

```text
winningThreshold = (roundCount + 1) / 2
```

| Event Rounds | Successful Rounds Required |
|---:|---:|
| 3 | 2 |
| 5 | 3 |
| 7 | 4 |
| 9 | 5 |
| 11 | 6 |

Because event lengths are odd, a fully resolved event cannot tie.

```text
Successful rounds > failed rounds
→ Overall Event Success

Failed rounds > successful rounds
→ Overall Event Failure
```

## 18. Rewards

### 18.1 Base reward

Every successful event grants one authored base Reward Step.

Void Fortune is not automatic. It is granted only when the event includes it as an authored reward.

### 18.2 Reward points

```text
Round Success          → 1 reward point
Critical Round Success → 2 reward points
```

### 18.3 Reward Step calculation

```js
rewardSteps = Math.min(
  3,
  1 + Math.floor((rewardPoints - winningThreshold) / 2)
);
```

The event gains one additional Reward Step for every complete two reward points beyond the event’s winning threshold.

### 18.4 Allocation limits

Each Reward Step may:

- add one reward item; or
- enhance an existing reward once.

Limits:

```text
Maximum Reward Steps: 3
Maximum separate reward items: 3
Maximum enhancements on one reward: 2
```

Example: a three-round event with two Critical Round Successes and one Round Success has 5 reward points. Its threshold is 2, so it receives 2 Reward Steps: either two items or one item enhanced once.

### 18.5 Possible authored rewards

Examples include:

- treasure;
- salvage;
- supplies;
- repair resources;
- route or tactical advantages for external systems;
- safe anchorage information;
- components;
- crew benefits;
- upgrade opportunities;
- Void Fortune;
- Field Repair Resources.

These are event-authored options, not universal automatic rewards.

## 19. Failure, Misfortune, and Critical Overall Failure

### 19.1 No reward on failure

An Overall Event Failure grants:

- no reward;
- no clue;
- no salvage;
- no Void Thread;
- no discovery.

Failure must still move the story into an authored consequence, retreat, diversion, emergency, capture, delay, repair situation, or other next state. It must not simply invite the players to repeat and farm the same event.

### 19.2 Failure points

```text
Round Failure          → 1 failure point
Critical Round Failure → 2 failure points
```

### 19.3 Negative Step calculation

```js
negativeSteps = Math.min(
  3,
  1 + Math.floor((failurePoints - winningThreshold) / 2)
);
```

### 19.4 Failure ladder

```text
1 Negative Step
→ Overall Event Failure
→ apply one base Misfortune

2 or 3 Negative Steps
→ Critical Overall Event Failure
→ apply an enhanced negative package
→ normally include or threaten a Void Scar as authored
```

Misfortunes may include travel delay, extra resource cost, temporary operational restriction, crew consequence, damaged room, or another persistent or temporary authored penalty.

A Void Scar created while the ship is already at maximum capacity triggers a Catastrophic Breakdown.

## 20. Ship Upgrades and Extensible Event Hooks

Station upgrades use an extensible hook system. The following effects are examples, not a closed list.

### 20.1 Common upgrade effects

An upgrade may:

- automatically reduce qualifying station DCs;
- grant a permanent `+1`, `+2`, or `+3` bonus to qualifying station rolls;
- grant a once-per-event rolled reaction that reduces Pressure;
- permanently increase one system’s Pressure Capacity, up to 5;
- prevent the first matching Hazard assigned to that station during the event;
- unlock or replace a station action;
- add an approach;
- unlock or modify a Risk Bid;
- grant or modify a Focus ability;
- increase Focus capacity or replenish Focus;
- redirect or prevent Pressure;
- remove, suppress, delay, replace, or escalate Hazards;
- change station order or allow an order reaction;
- protect another station;
- modify a result degree;
- allow a reroll or roll-twice effect;
- prevent or weaken a Void Scar;
- improve repair cost or time;
- enable field repair;
- modify resource use;
- unlock special rewards, vignettes, or event branches.

### 20.2 Passive DC reduction

A qualifying passive upgrade applies before the selected Risk Bid:

```text
Final DC = Base Action DC - upgrade reductions + Risk Bid
```

Total Arcflight DC reduction remains capped at 5.

### 20.3 Permanent roll bonus

Permanent station bonuses use values from `+1` to `+3` and remain subject to the total Arcflight `+5` roll-bonus cap.

### 20.4 Once-per-event pressure reaction

A station upgrade may grant a reaction such as:

| Result | Example Effect |
|---|---|
| Critical Success | Reduce station Pressure by 2 |
| Success | Reduce station Pressure by 1 |
| Failure | No change |
| Critical Failure | Increase station Pressure by 1 |

This is a template. The upgrade may author different outcomes.

### 20.5 Prevent first Hazard

A station upgrade may prevent the first matching Hazard that would be assigned to its system during an event.

When a Pressure Breach creates both a Hazard and Void Scar:

- the upgrade may prevent the Hazard;
- the Void Scar is still proposed;
- Pressure still resets to zero.

A stronger upgrade may explicitly prevent both, but that is a separate effect.

### 20.6 Required upgrade fields

Every upgrade effect defines:

- owner and affected station or system;
- trigger;
- timing;
- scope and matching tags;
- passive or activated behavior;
- roll requirement, if any;
- uses and refresh timing;
- duration;
- four outcomes when rolled;
- stacking behavior;
- visibility and narration.

An upgrade must not silently create a fourth station action. It may replace or modify one of the three authored action slots.

## 21. Event Closeout and Recovery

### 21.1 Closeout order

After the final round:

1. determine the final round result;
2. update Momentum from that round;
3. determine Overall Event Success or Failure;
4. calculate Reward Steps or Negative Steps;
5. resolve unresolved Hazard closeout effects;
6. process any resulting Pressure Breaches;
7. propose new Void Scars or Catastrophic Breakdowns;
8. present the complete package to the GM;
9. GM confirms persistent changes;
10. play the ending vignette;
11. record event history;
12. clear temporary event state.

### 21.2 GM closeout review

The GM sees:

- overall result;
- successful and failed rounds;
- Reward Steps or Negative Steps;
- selected rewards;
- Misfortunes;
- new or removed Void Scars;
- unresolved Hazard consequences;
- system damage;
- Catastrophic Breakdown status;
- all proposed persistent changes.

The GM may review and correct invalid state, but should not ordinarily rewrite legitimate player rolls or calculated results.

### 21.3 Temporary state cleared

At closeout:

- Momentum resets to 0;
- unused Focus disappears;
- Pressure resets to 0 after closeout effects;
- pending station benefits expire;
- unconsumed Risk Bid benefits expire;
- temporary Focus penalties expire;
- round-order restrictions expire unless persistent;
- temporary Hazard suppression ends;
- unresolved Hazards apply their authored closeout effect and are removed.

### 21.4 Persistent state

Persistent state may include:

- Void Scars;
- Catastrophic Breakdowns;
- ship damage;
- consumed or gained resources;
- reward items;
- Field Repair Resources;
- permanent Misfortunes;
- disabled rooms or systems;
- event history.

No persistent ship mutation is committed until GM closeout approval.

## 22. Event Session Lifecycle

Canonical session states:

```text
Setup
→ Round Introduction
→ Crew Planning
→ Plan Locked
→ Station Resolution
→ Round Closeout
→ Next Round
→ Event Closeout Review
→ Persistent Application
→ Completed
```

Exceptional states:

```text
Paused
Emergency Response
Aborted
Recovery Required
```

### 22.1 Setup validation

Before Round 1:

- Event Definition is valid.
- Ship exists and is Arcflight-enabled.
- Installed hull and Void Scar Capacity are readable.
- Only one operator occupies each station.
- No operator occupies multiple stations.
- Every operator has usable PF2e statistics.
- Referenced upgrades and Scars are valid.

### 22.2 Plan-lock validation

Before resolution:

- every occupied station selected exactly one action;
- every selected action has a valid approach;
- every selected Risk Bid is offered by that action;
- no station selected more than one bid;
- no more than three stations selected bids;
- all required targets are valid;
- every occupied station appears once in the order;
- no unoccupied station appears in the order.

### 22.3 Pausing and resuming

Safe pause points include:

- during planning;
- between Action Segments;
- after a reaction resolves;
- after round closeout;
- during closeout review.

The system should not pause halfway through applying one atomic outcome branch.

### 22.4 Recovery checkpoints

Create recoverable checkpoints:

- before plan lock;
- before each Action Segment;
- before each reaction;
- before round closeout;
- before Emergency Response;
- before persistent closeout application.

Recovery must not duplicate rolls, Pressure, Hazards, consumed uses, rewards, or persistent mutations.

### 22.5 Disconnection

A disconnected user does not vacate the station. The GM may:

- wait;
- resolve the assigned operator on the user’s behalf;
- temporarily grant another user control of the same operator;
- use the already locked action.

This transfers control, not station assignment.

### 22.6 Abort

**Cancel Setup:** before Round 1 resolution; no persistent consequences.

**Abort Active Event:** stop further station resolution, resolve applicable Hazard closeout effects, provide no reward, and apply the event’s authored abort consequence after GM review.

## 23. Visibility and Authority

### 23.1 Shared planning information

Players normally see:

- occupied stations;
- selected actions;
- selected approaches;
- selected Risk Bids;
- required targets;
- proposed resolution order;
- known cross-station benefits;
- current Momentum, Pressure, and revealed Hazards.

### 23.2 Choice transparency

Before committing to a Risk Bid or Focus ability, the acting player must see:

- the check being attempted;
- DC or DC adjustment;
- intended benefit;
- known Failure effect;
- known Critical Failure effect;
- target.

GM-only information may conceal future narrative details, discoveries, or unrevealed escalation, but must not secretly replace the displayed mechanical stakes with unrelated punishment.

### 23.3 GM authority

The GM-owned session is authoritative. Players submit selections and reactions, but the runtime validates and commits official state.

GM correction tools may address:

- invalid ownership;
- accidental duplicate submissions;
- wrong targets;
- incorrect order;
- failed external roll integration;
- broken media or socket state;
- recovery from an interrupted operation.

Corrections after plan lock are recorded in the audit history.

## 24. Event Definition Requirements

Every handcrafted event must include:

- stable unique `eventId`;
- title, summary, level/DC source, tags, and media fallbacks;
- odd `roundCount` from 3 to 11;
- event introduction;
- round definitions in complete order;
- three actions for every potentially occupied station in every round;
- one to two approaches per normal action, with a rare justified third approach;
- base action outcome branches;
- available Risk Bid tiers and all four bid branches;
- Focus abilities and reaction definitions;
- Hazard definitions and closeout behavior;
- reward options and enhancement tiers;
- Misfortune options and enhancement tiers;

## 25. Validation Rules

An Event Definition is invalid unless:

- `eventId` is stable and unique;
- round count is 3, 5, 7, 9, or 11;
- round numbers are complete, unique, and ordered;
- referenced stations exist;
- every active station has exactly three actions per round;
- every action ID is unique;
- every action has at least one valid approach;
- no normal action exceeds two approaches;
- an exceptional third approach declares a meaningful distinction;
- every action has a valid PF2e check source and DC source;
- every action defines all four outcomes;
- Risk Bid tiers are only 2, 5, or 8;
- every Risk Bid defines all four outcomes;
- every Focus ability defines trigger, timing, cost, target, DC, and four outcomes;
- every Hazard defines activation, effect, response, and closeout behavior;
- every Void Scar defines operational effects and repair requirements;
- every Catastrophic Breakdown defines Emergency Response outcomes;
- every reward defines a base form;
- reward enhancements do not exceed two tiers per item;
- all media references have valid fallbacks;
- every persistent effect requires GM confirmation;
- all player-facing risky choices expose known stakes.

The validator should warn when:

- an event repeatedly pressures one system without relief opportunities;
- a round can create more Hazards than the crew can reasonably address;
- Risk Bid risks are disproportionate to their benefits;
- no action can reduce Pressure or address a likely Hazard in a major event;
- a long event lacks meaningful round-to-round action changes;
- an authored branch or target is unreachable.

## 27. Canonical Core Loop

```text
GM selects authored event and ship
→ assign one character or named NPC to each occupied station
→ lock station assignments for the event
→ begin Round 1 with Focus and Momentum 0
→ show round-specific cinematic and stakes
→ present 3 new actions per occupied station
→ choose action, approach, base DC or Risk Bid, and target when needed
→ choose and lock station resolution order
→ resolve each Action Segment with Focus, reactions, upgrades, and special abilities
→ aggregate success/failure units
→ determine round result
→ update Momentum
→ apply Pressure, Hazards, and Breaches
→ continue through all authored rounds
→ determine overall result
→ calculate rewards or negative package
→ resolve unresolved Hazards
→ propose Void Scars or Catastrophic Breakdown
→ GM reviews and applies persistent closeout
→ record event history
→ clear temporary state
```
