# Arcflight Gameplay V3 — Milestone 12 Task 3

## Station Resolution and PF2e Check Vertical Slice

Task 3 begins only after the M12 plan-lock transition. It owns the GM
resolution view and the first real PF2e station-check loop; it does not own
round closeout, rewards, Focus, reactions, or persistent application.

### State boundary

`plan-locked / active / lock-readiness` may enter Resolution exactly once.
The canonical `applyVoyageEncounterResolutionTransition` API creates the
phase-start snapshot and enters `station-resolution / active / resolution`.
The committed station order remains authoritative. Only occupied stations
are resolved, in committed order. Each station has its persisted action,
approach, Risk Bid, base DC, final DC, and Momentum context.

### Commands

The public M11 command envelope remains authoritative. Task 3 adds the GM
command kinds `resolution-start` and `action-segment`.

* `resolution-start` payload is exactly `{ phaseStartSnapshotId }`. The
  phase-start snapshot ID is generated by trusted runtime code; callers may
  request only the command envelope and cannot author state or calculated
  values.
* `action-segment` is accepted only from the trusted PF2e execution boundary.
  Its normalized execution result is checked against the durable pending
  check, including source UUID, statistic, final DC, roll mode, sequence, and
  degree-of-success result. A public caller cannot supply a DC, roll, result,
  next state, or event.

Both commands require the authenticated connected active GM, the current
authority epoch, and the expected session revision. Replays return the
isolated stored response with no write; changed request IDs conflict; stale,
forged, malformed, or unsupported commands write nothing.

### Durable pending checks

Before a PF2e roll, trusted runtime code binds each authored character check
to the assigned operator UUID, calls the canonical pending-check preparation
API, and persists the resulting pending-check state and domain evidence. No
live Actor, Statistic, Check, or Foundry object is stored in the JournalEntry.
The persisted pending check contains only canonical plain data. A roll is
executed exactly once by `executeVoyagePf2ePendingCheckInFoundry`; its
normalized result is then applied with
`applyVoyageEncounterPendingCheckResult` and persisted as an append-only
resolution event.

### Authored checks

The registered M12 definition supplies three ordinary PF2e statistic options
for every authored action, with a fixed base DC of 18 and public secrecy.
The selected Risk Bid contributes its canonical +2, +5, or +8 adjustment;
the domain DC cap and all existing Risk Bid rules remain authoritative.

### Read and UI boundary

`readVoyageEventSessionResolution(sessionId)` returns an isolated GM-only
resolution projection containing the committed order, current station,
operator/action/approach/Risk Bid/DC/Momentum context, pending/resolved
status, and resolved degree data. It omits raw session persistence evidence,
authority internals, and live PF2e objects. Reads never write. The Event
Manager adds a Resolution tab while preserving the existing Overview, Crew
Plan, Resolution Order, and Plan Review tabs. After plan lock, planning
controls are read-only.

### Completion boundary

After the final occupied station resolves, Task 3 reports Resolution complete
awaiting round closeout. It does not advance the round, calculate Momentum or
round results, apply rewards, invoke M10 closeout, or perform any Actor write.
