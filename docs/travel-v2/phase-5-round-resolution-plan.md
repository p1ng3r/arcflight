# Travel v2 Phase 5 round resolution plan

## 1. Phase 5 purpose

Phase 5 owns Travel v2 round finalization and event progression after the Phase 4 GM pressure loop has completed its session-local work. Phase 4 answers, “What pressure outcome did the GM apply or correct for this round?” Phase 5 should answer, “Is this round now resolved, and is the runner ready to move forward?”

This phase must remain conservative. Round resolution is still runner-session state only: it records the GM’s decision that the current round is finalized, preserves the effective pressure/correction evidence used for that decision, and exposes whether the event is ready for completion after the last round. It must not persist consequences to actors or items, announce results to players, or hand off fortune/scar rewards until later explicit phases add those responsibilities.

## 2. Round lifecycle states

Use a small state progression that matches the current runner pressure loop and leaves room for later persistence:

```text
previewing → pressure-applied → finalized → event-complete-ready
```

- `previewing`: The current round has a preview model but no effective pressure application record. The round is unresolved. The GM may still choose a valid preview outcome, or a later helper may allow an explicit zero-pressure/skipped-pressure path if that is intentionally designed.
- `pressure-applied`: The current round has an effective pressure application record from Phase 4. This may be the original application or the corrected application after Hard Correction. The round is still unresolved until the GM finalizes it. Before finalization, the GM may use the existing Phase 4 correction flow when its guards allow it.
- `finalized`: The current round has a session-local round resolution record. The round is resolved and locked for Phase 5 purposes. Pressure application, pressure correction, and finalization controls should be disabled for that round.
- `event-complete-ready`: The finalized round was the last event round. The runner may show a completion-readiness summary, but completion remains a later explicit step and must not mutate actors/items or issue rewards automatically.

A round is **unresolved** when there is no matching finalization record for its `roundIndex`/`roundNumber`. A round is **pressure-applied** when `prepareTravelV2PressureApplicationState` or a Phase 5 read model can identify an effective current-round pressure application record. A round is **finalized** when a matching record exists under the session-local round resolution container. Editable state before finalization is limited to the Phase 4 GM pressure choice/correction and any Phase 5 finalization note/reason. After finalization, the effective outcome, pressure application snapshot, correction snapshot, station summary snapshot, and finalization note are locked unless a later rollback/admin phase explicitly defines how to reopen them.

## 3. Finalization inputs

A GM can finalize a Travel v2 round only when all required inputs are available and no blocking state remains:

- An active Travel v2 runner session exists.
- The session has a current round with a stable `roundIndex` and, when available, `roundNumber`.
- The current round is not already finalized.
- An effective pressure application/outcome exists for the current round, unless a later implementation explicitly supports a zero-pressure or skipped-pressure finalization path and records that reason.
- Station result summaries are available when the current runner model already exposes them; if not exposed, the finalization helper should store `null` or an empty summary rather than inventing content.
- No unresolved correction state, blocked correction action, or pending GM-only pressure action is in progress.
- The runner session is not already completed.

The first implementation should prefer blocking finalization when evidence is missing. Any exception, such as a zero-pressure round, should be explicit in the helper result and in the finalization record.

## 4. Finalization record

Finalized rounds should be recorded in a session-local container that mirrors the Phase 4 pressure application/correction record style:

```js
session.travelV2RoundResolutions = {
  records: [roundResolutionRecord]
};
```

Recommended record shape:

```js
const roundResolutionRecord = {
  roundIndex,
  roundNumber,
  finalizedAt,
  helperVersion,
  lifecycleState: "finalized",
  effectiveOutcomeKey,
  pressureApplicationRecord,
  correctionRecord,
  stationSummary,
  notes,
  reason
};
```

Field guidance:

- `roundIndex`: Zero-based current round index used by the runner.
- `roundNumber`: Human-facing round number when known.
- `finalizedAt`: ISO timestamp supplied by options or generated by the helper.
- `helperVersion`: Version number for the Phase 5 finalization helper.
- `lifecycleState`: Usually `"finalized"`; a read model can derive `"event-complete-ready"` when this is the last round.
- `effectiveOutcomeKey`: Outcome key from the effective Phase 4 pressure application record.
- `pressureApplicationRecord`: Deep-cloned snapshot of the effective application record.
- `correctionRecord`: Deep-cloned snapshot of the matching correction record when present; otherwise `null`.
- `stationSummary`: Deep-cloned snapshot of current station result summaries when already exposed by the runner model; otherwise `null` or an empty object.
- `notes` / `reason`: Optional GM note or helper-supplied reason, especially for an explicitly allowed skipped/zero-pressure finalization.

The helper should not store live object references. Snapshots protect the finalization evidence from later session-local edits and make duplicate/idempotent checks simpler.

## 5. Duplicate and finality guards

Phase 5 should treat finalization as a one-way session-local decision for the current round.

- If a matching finalization record already exists for the round, repeated finalization should not append a duplicate record.
- The first implementation may either return a blocked result (`ok: false`, `alreadyFinalized: true`) or an idempotent success (`ok: true`, `finalized: false`, existing record returned). The preferred conservative default is blocked-with-existing-record so the GM receives clear feedback that no new work occurred.
- Matching should use `roundIndex` first and `roundNumber` as a fallback, consistent with existing pressure application matching.
- Once finalized, Phase 4 pressure correction is no longer allowed for that round.
- If a GM needs to fix a finalized round, that is out of scope for Phase 5A–5F and should be handled by a later explicit rollback/admin phase.

Future correction helpers should include a finalized-round guard before reversing pressure. Future finalization helpers should include a pressure-application guard before writing a resolution record.

## 6. Runner advancement

Finalization and runner advancement should be split into small reviewable slices:

- **5B — Round finalization state model:** Add a read-only helper that derives current round lifecycle state, finds any matching finalization record, finds the effective pressure application/correction records, and reports whether finalization is currently available.
- **5C — Session-local round finalization helper:** Add a helper that deep-clones the runner session, appends one round resolution record, and returns structured success/blocking feedback without mutating actors/items.
- **5D — GM runner internal finalize action path:** Wire the helper to the runner’s internal GM action handling without visible player automation.
- **5E — Visible finalize controls and feedback:** Add GM-facing finalize controls and status messages in the runner UI, disabled when blocked or already finalized.
- **5F — Event completion readiness summary:** When the finalized round is the final event round, derive and display `event-complete-ready` / completion-summary-ready state.
- **5G — Final consequence/reward handoff plan or implementation:** Define or implement the later explicit boundary for fortune/scar reward handoff and any persistence, depending on the approved scope at that time.

Advancing to the next round should happen only after a round has a finalization record. Whether the first implementation increments a session-local current-round pointer immediately or merely enables a separate “advance” action should be decided in 5D/5E. The conservative preference is to keep “finalize” and “advance” as distinct internal operations until the UI proves the combined flow is safe.

## 7. Event completion boundary

When the last event round is finalized, the runner should derive a completion-readiness state such as `event-complete-ready` or `completion-summary-ready`. That state may summarize finalized round records and effective outcomes so the GM can review the event before completing it.

This readiness state must not automatically:

- Mutate actor data.
- Mutate item data.
- Award fortune.
- Apply scars.
- Emit chat messages.
- Emit sockets.
- Change player station cards.

Actual event completion, persistence, consequence application, and reward handoff remain later explicit phases.

## 8. Safety boundaries

Phase 5 round resolution must preserve the Phase 4 safety boundaries:

- No actor mutation.
- No item mutation.
- No socket emission.
- No chat output.
- No player station card changes.
- No PF2E resolution changes.
- No Hard Correction changes beyond adding finalized-round guards in later implementation slices.
- No pressure math changes.
- No automatic finalization during render.
- No hardcoded content in UI logic.
- No fortune/scar reward handoff unless a later explicit phase adds it.

All Phase 5 helpers should be deterministic over their session input except for timestamps supplied by options or generated at the helper boundary. UI render code may display derived finalization state but must not create finalization records as a side effect.

## 9. Proposed Phase 5 task list

- **5A — Plan and guardrails:** Document the lifecycle, inputs, record shape, duplicate guards, advancement split, event completion boundary, and hard safety boundaries.
- **5B — Round finalization state model:** Implement a read-only model that identifies unresolved, pressure-applied, finalized, and event-complete-ready states for the active round.
- **5C — Session-local round finalization helper:** Implement the clone-and-append finalization helper with duplicate guards and snapshot records.
- **5D — GM runner internal finalize action path:** Connect the helper to internal runner actions and preserve structured feedback for blocked/finalized states.
- **5E — Visible finalize controls and feedback:** Add GM-only controls, disabled states, and clear messages for finalization availability and finality.
- **5F — Event completion readiness summary:** Display a review summary after the final round is finalized without completing or persisting consequences.
- **5G — Final consequence/reward handoff plan:** Plan, and only if explicitly approved then implement, the boundary from completion readiness to fortune/scar rewards and persistence.
